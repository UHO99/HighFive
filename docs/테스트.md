# 쿠폰 발급 동시성 벤치마크 — 테스트 환경 & 측정 방법

`benchmark/crud`, `benchmark/redis`, `benchmark/kafka` 아래 JUnit 테스트로 측정한 결과를 재현하거나
다른 환경에서 다시 잴 때 참고하는 문서. 같은 로컬 PC에서 세 구현을 순차 실행한 1회 측정 기준이며,
정확한 재현을 위해서는 아래 조건을 최대한 맞춰야 한다.

## 1. 로컬 PC 사양

| 항목 | 값 |
| --- | --- |
| OS | Windows 11 Pro 64bit (Build 26200) |
| CPU | AMD Ryzen 5 7530U (6 Core / 12 Thread) |
| RAM | 31.4 GB |
| 디스크 | 로컬 SSD (MySQL/Redis/Kafka 전부 로컬 Docker/설치) |

## 2. Java / JVM

| 항목 | 값 |
| --- | --- |
| JDK | 21.0.10 LTS (HotSpot, mixed mode) |
| 빌드 도구 | Gradle 9.6.1 (wrapper) |
| 테스트 실행 힙 | `build.gradle`의 `test { maxHeapSize = "4g" }` |

**중요 — 힙 크기를 반드시 4g 이상으로 설정할 것.** Gradle 테스트 워커 JVM의 기본 힙은 512MB인데,
`CrudConcurrencyTest`처럼 가상 스레드 100,000개가 동시에 실행되는 테스트는 이 기본값으로 돌리면
`OutOfMemoryError: Java heap space`로 죽는다 (실제로 이번 측정 중 재현됨 — 락 대기 중이던
가상 스레드/커넥션이 힙을 다 먹었고, 프로세스가 좀비 상태로 남아 DB 락까지 붙잡고 있었다).
`maxHeapSize`를 올린 뒤로는 100,000 동시 요청이 안정적으로 처리된다.

각 벤치마크 테스트는 `Runtime.getRuntime().totalMemory() - freeMemory()`를 100ms 간격으로
샘플링해서 **피크(최댓값) 사용 힙**을 리포트에 함께 찍는다 (GC 타이밍에 따라 순간값은 흔들리므로
"피크"만 신뢰할 수 있는 지표로 본다 — 평균값은 별 의미가 없어서 안 찍음).

## 3. DB / 스키마

| 항목 | 값 |
| --- | --- |
| MySQL | 8.0.40 (`ureca:ureca@localhost:3308/highfive`) |
| Flyway | `spring.jpa.hibernate.ddl-auto=validate`, 마이그레이션은 `db/migration`, 시드는 `db/seed`에서 별도 로드 |
| 현재 스키마 버전 | V8 (`V1__init` ~ `V8__add_coupon_issued_quantity`, 시드는 `V5__sample`) |

관련 테이블 (실측 시점 `SHOW CREATE TABLE` 기준, 컬럼만 요약):

- **`coupon`**: `id, name, total_quantity, start_at, end_at, status(READY/OPEN/CLOSE), created_at, updated_at, issued_quantity`
- **`coupon_issue`**: `id, user_id, coupon_id, status(ISSUED/USED/CANCELED/EXPIRED), issued_at, used_at, canceled_at, expired_at` — `UNIQUE(user_id, coupon_id)`, `INDEX(coupon_id, status)`, `user_id`/`coupon_id` 각각 FK
- **`users`**: `id, email(UNIQUE), created_at, name, phone`

`coupon_issue.user_id`가 `users.id`를 FK로 참조하므로, 벤치마크가 임의의 `userId` long 값을 그냥
쓰면 발급 이력을 남기는 경로(Redis Stream 배치)에서는 FK 위반으로 조용히 실패한다 — 반드시
실제 `users` row를 먼저 만들고 그 id를 써야 한다 (`CrudConcurrencyTest`/`RedisConcurrencyTest`처럼
재고 값만 다루는 경로는 `coupon_issue`를 안 건드리므로 해당 없음).

## 4. Redis / Kafka

| 항목 | 값 |
| --- | --- |
| Redis | `redis:latest` 컨테이너, 실측 시점 서버 버전 8.10.0, `localhost:6379` |
| Kafka | `confluentinc/cp-kafka:latest` 컨테이너, 실측 시점 8.3.1-ccs, `localhost:9092` |
| 토픽 | `coupon-issue-request`, 파티션 3 / replicas 1 (`CouponKafkaTopicConfig`) |
| 컨슈머 | `concurrency=12` (`CouponIssueConsumer`) — 파티션이 3개뿐이라 실제 동시 소비 가능한 스레드는 최대 3개, 나머지 9개는 유휴. 파티션 수와 컨슈머 concurrency가 안 맞는 상태로 측정됨 (수정하지 않고 현재 설정 그대로 잰 값) |
| `MAX_POLL_RECORDS` | 기본 500 (`CouponKafkaConsumerConfig`) — 배치 크기 민감도는 별도로 100/500/2000 세 값으로 재측정 |

## 5. 측정 방법론

- **컨트롤러(HTTP)를 거치지 않는다.** 각 구현의 진입점을 테스트에서 직접 호출한다
  (`couponRequestProducer.request(...)`, `RedisCouponStockTestService.decreaseStock(...)`,
  `couponService.decreaseStockBatch(...)`). 네트워크/톰캣 스레드 오버헤드를 지표에서 뺀 순수
  구현 성능만 재려는 의도.
- **동시성**: `Executors.newVirtualThreadPerTaskExecutor()`로 요청 수만큼 가상 스레드를 만들어
  한 번에 제출한다.
- **동기 vs 비동기 처리 완료 판정**: CRUD/Redis는 각 호출의 리턴값으로 그 자리에서 성공/실패를
  안다. Kafka는 프로듀서가 큐잉만 하고 끝나므로, 컨슈머 내부 `AtomicInteger`(processedCount)가
  요청 수와 같아질 때까지 `Awaitility`로 기다린 뒤에야 "처리 완료" 시점을 알 수 있다 — 이 대기
  시간까지 포함해서 총 소요 시간을 잰다.
- **정합성 판정**: 최종 DB(or Redis) 재고가 정확히 0인지, 성공 발급 건수가 초기 재고와 일치하는지,
  오버셀(음수 재고)이 없는지 어서션으로 확인한다. 중복 발급 체크는 Kafka만 컨슈머가 자체적으로
  집계하고 있고(개념상 필요), CRUD/Redis는 원자적 단일 연산이라 애초에 중복이 발생할 수 없는
  구조라 별도로 재지 않는다.
- **재현 시 유의**: 같은 조건이라도 GC 타이밍/OS 스케줄링에 따라 총 소요 시간이 회차마다 10~30%
  정도 흔들린다 (예: Kafka 기본 설정을 두 번 연속 잰 값이 9.67초 / 7.83초로 달랐음). 결론을 내릴
  땐 단발 측정 하나에 기대지 말고 최소 2~3회 재현해서 편차를 같이 보는 걸 권장한다 — 이번 문서의
  수치도 대부분 1회 측정이라 그 한계를 그대로 갖고 있다.
