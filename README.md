## 프로젝트 개요

Redis Stream 기반으로 대량 트래픽의 선착순 쿠폰 발급을 처리하고, 그 결과를 비동기로 DB에 적재·동기화·검증까지 하는 백엔드 시스템과, 이 파이프라인을 실시간으로 관찰/부하테스트할 수 있는 관리자 대시보드로 구성되어 있습니다.

## 1. 실행 방법

### 요구사항
- Docker / Docker Compose

### 클론
```bash
git clone https://github.com/UHO99/HighFive.git
cd HighFive
```

### 백엔드 + MySQL + Redis + K6 이미지
```bash
cd backend
docker compose build k6 && docker compose up -d --build
```
대시보드의 "테스트 시작" 버튼은 백엔드가 호스트 도커 소켓으로 k6 컨테이너를 띄워서 동작하는데, `k6` 서비스는
`docker compose up`만으로는 안 만들어진다.
그래서 `build k6`를 먼저 실행해 이미지를 준비한 다음 나머지를 띄운다.

확인:
```bash
curl http://localhost:8080/1
```

기본 계정은 `ureca`/`ureca`입니다. 바꾸고 싶으면 실행 시 환경변수로 넘기면 됩니다:
```bash
DB_USER=myuser DB_PASSWORD=mypass docker compose up -d
```

종료:
```bash
docker compose down       # 컨테이너만 정지 (데이터 유지)
docker compose down -v    # DB 데이터까지 초기화
```

### K6 시나리오 추가
시나리오 목록은 `backend/k6/` 디렉터리를 스캔하는 게 아니라, 백엔드의 `K6Scenario` enum
(`global/common/enums/K6Scenario.java`)에 정의된 것만 대시보드에 뜨고 실행도 된다 - 클라이언트가 보낸
시나리오 id로 임의의 파일을 실행시키지 못하게 막는 화이트리스트다. 그래서 새 시나리오를 추가하려면:

1. `backend/k6/내스크립트.js` 작성. `BASE_URL`/`COUPON_ID`를 기존 스크립트들과 같은 방식으로 읽어야 한다:
   ```js
   const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';
   const COUPON_ID = __ENV.COUPON_ID || '1';
   ```
2. `K6Scenario` enum에 상수 추가 (`id, file, name, description, rampUp, hold, targetVus, configurable, advanced`)
   - 앞의 일곱 개는 대시보드 시나리오 다이얼로그에 그대로 노출되는 값이고, 뒤의 두 개는 실행 전에
   어떤 입력창을 띄울지를 정한다:
   - `configurable` : 재고(`STOCK`)/동시접속(`MAX_VUS`) 입력. 재고는 선택한 쿠폰의 실제 값을 자동으로 쓴다.
   - `advanced` : 요청배수(`REQUEST_RATIO`)·유입방식(`ARRIVAL`/`DURATION`)·연타(`SPAM_RATIO`/`SPAM_CLICKS`)까지 입력.
     스크립트가 그 env var를 실제로 읽을 때만 true로 둘 것 - 안 읽는 스크립트에 true를 주면 입력창만
     뜨고 값은 무시된다.
3. 백엔드 재빌드 + k6 이미지 재빌드 (둘 다 해야 목록/실행이 새 시나리오를 반영한다):
   ```bash
   docker compose build k6 && docker compose up -d --build
   ```
   enum엔 추가했는데 이미지 빌드를 깜빡하면, 실행 시 "아직 이미지에 반영되지 않았습니다" 에러로 바로
   알려준다.

```bash
https://uho99.github.io/HighFive/
```

### 1. Redis → DB 비동기 반영에서 지연 허용 범위는 어느 정도인지

Redis에 먼저 요청을 적재하고 스케줄러가 주기적으로 읽어 DB에 반영하는 구조를 계획 중입니다. 이 시차를 실무에서는 보통 어느 정도까지 허용하는지, 사용자 응답에 영향이 안 가도록 어떻게 설계하는지 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

“주기를 얼마로 잡을지” 자체가 성능과 직결되는 문제이므로, 부담이 크다면 폴링 주기를 늘리는 방향으로 조절하는 게 가장 기본적인 대응이다.

자동 갱신 대신, 사용자가 원할 때 직접 새로고침할 수 있는 버튼을 두는 방식도 대안이 될 수 있다.

실제 운영 대시보드 사례로는 그라파나(Grafana) 같은 툴이 이런 주기 관리를 어떻게 하는지 참고해볼 만하다.

</details>

---

### 2. 리소스 생성 시점 vs 활성화 시점, 캐시 적재 타이밍

저희는 쿠폰을 생성하는 시점(READY)과 실제로 오픈(OPEN)하는 시점을 분리해두고, Redis에 재고를 올리는 건 오픈하는 순간에만 하고 있습니다.

이렇게 "리소스를 만드는 시점"과 "그 리소스를 실제로 활성화하는 시점"이 다를 때, 캐시에 값을 미리 올려둘지 활성화 시점에 올릴지를 실무에서는 어떤 기준으로 정하는지 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

지금 방식(생성과 오픈을 분리하고, 오픈 시점에만 Redis 재고를 적재하는 것)을 실무에서도 그대로 쓸 것 같다.

캐시에는 미리 값을 올려두되 상태를 READY로 표시해두고, 정해진 시점(오픈 시각)이 되면 그 상태를 활성화로 전환하는 방식이 일반적이다.

지금 설계에 큰 문제는 없어 보인다.

</details>

---

### 3. 대량 이력 조회 API의 페이지네이션 방식

저희는 관리자가 특정 쿠폰의 전체 발급 이력(수만~수십만 건)을 조회하는 API를 두고 있는데, 지금은 커서(cursor) 기반으로 페이지네이션하고 있습니다.

이렇게 이력이 매우 커질 수 있는 조회 API에서, 실무 어드민 화면은 보통 cursor 방식과 offset 방식 중 뭘 쓰는지, "전체 조회"를 아예 허용 안 하는 정책은 어떤 기준으로 정하는지 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

수십만 건 규모라면 페이지네이션은 반드시 필요하다.

본인이 속한 환경에서는 커서 방식을 현재 사용하고 있지는 않지만, 관리자 페이지라 해도 페이징 자체는 필요해 보인다.

페이징 대신 필터링 기능(예: 상태별, 기간별 조회)을 넣는 것도 대안이 될 수 있다.

어떤 방식이 나을지는 팀 내부 소통으로 결정할 사안이고, 실제로 두 방식을 바꿔가며 테스트해보고 더 나은 쪽을 선택하는 걸 권한다.

이때 쿼리 실행 계획(쿼리 플랜)을 확인해보면, 인덱스를 잘 태우는지에 따라 방식 간 속도 차이가 크게 날 수 있다.

</details>

---

### 4. 비관적 락 + 가상 스레드(Virtual Thread) 조합의 운영 안정성

저희는 동시성 제어에 DB 비관적 락과 Java의 가상 스레드(Virtual Thread)를 함께 써서 부하 테스트를 진행했습니다.

이 조합이 실제 운영 환경에서도 안정적인지, 가상 스레드와 락을 같이 쓸 때 특별히 주의해야 하는 함정이 있는지 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

실무 경험상 가상 스레드는 아직 널리 쓰이는 편이 아니고, 비관적 락도 자주 쓰는 방식은 아니다.

업데이트가 빈번하게 일어나야 하는 상황에서 락을 걸면 그 자체로 성능 저하가 우려된다.

또한 가상 스레드 환경에서 특정 방식으로 락을 걸면 락이 제대로 안 걸리는(의도대로 동작하지 않는) 경우가 있다고 들었는데, 정확한 조건은 추가로 더 찾아볼 필요가 있다.

</details>

---

### 5. 캐시 복구 시, 상태값을 필터링해서 재계산하는 것이 맞는지

저희는 Redis 재고 키가 유실됐을 때(예: Redis 재시작), DB에서 다시 계산해 복구하는 로직을 두고 있습니다.

이때 "현재 유효한 상태"의 건수만 세어서 복구값을 계산하는데(취소/만료된 건 제외), 이런 접근이 맞는지, 실무에서는 캐시 복구 시 재계산 범위를 어떤 기준으로 정하는지 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

Redis에는 활성화하면 메모리 데이터를 파일로 남겨주는 영속화 옵션(AOF/RDB)이 있으니, 이걸 켜서 활용해보는 걸 권한다.

다만 이 옵션을 켜더라도 복구 후 데이터 정합성이 맞는지는 별도로 확인이 필요하다.

안정성을 더 높이고 싶다면 Redis를 2대(이중화) 구성하는 것도 방법이다.

복구 시에는 필요한 데이터만 필터링해서 복구하면 되는데, 이렇게 부분적으로만 복구하면 DB에 남아있는 실제 값과 서로 안 맞을 수 있으니 그 가능성은 염두에 둬야 한다.

</details>

---

### 6. 부하 테스트 파라미터 — 자동 계산 vs 사람 입력의 기준

부하 테스트를 실행할 때, 재고 수량 같은 값은 시스템이 자동으로 채워주고, 요청 수 같은 값은 사람이 직접 입력하게 하고 있습니다.

"자동으로 채워도 되는 값"과 "반드시 사람이 결정해야 하는 값"을 나누는 기준을 실무에서는 어떻게 잡는지 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

쿠폰 재고처럼 시스템이 스스로 정한 고정값은 자동으로 채워도 되지만, 실제 사용자가 몇 명이나 몰릴지는 시스템이 통제할 수 없는 외부 변수이므로 이 부분이야말로 직접 테스트해봐야 하는 대상이다.

이미 쌓여있는 더미데이터나 과거 이력이 있다면 그걸 기준값으로 활용하면 되고, 앞으로 트래픽이 더 늘어날 것으로 예상된다면 그만큼 더 많은 데이터를 채워서 테스트해보면 된다.

</details>

### 7. 짧은 이벤트를 대시보드에 실시간으로 보여주는 방법

전체 처리가 수십 초 안에 끝나는 짧은 이벤트(부하 테스트)를 대시보드 화면에 실시간으로 보여주고 싶습니다.

이렇게 지속 시간이 아주 짧은 이벤트를 반영할 때, 폴링 주기를 얼마나 짧게 잡아야 하는지, 폴링이 아닌 다른 방식(WebSocket, SSE 등)을 언제부터 고려해야 하는지 실무 기준이 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

이 대시보드처럼 보는 사람이 관리자 몇 명으로 한정된 화면이라면, 폴링 방식으로도 충분하다.

반면 일반 사용자가 다수 접속해서 보는 화면이라면 폴링 자체가 서버에 부담이 될 수 있어 다른 방식을 고려해야 한다.

지금 수준(관리자 전용 부하 테스트 대시보드)에서는 폴링으로 가도 되고, 지금 쓰고 있는 1초 주기가 실제로 부담 없이 잘 동작한다면 그대로 유지해도 괜찮다.

### 8. "처리된 순간"과 "기록된 시각"이 다를 때, 어느 걸 보여줘야 하는지

이렇게 "진짜 처리 순서"와 "DB에 남는 시각"이 어긋날 수 있는 시스템에서, 화면에는 어느 걸 기준으로 보여주는 게 맞는지 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

한 번 확정된 대상을 영구 제외하는 방향은 필요해 보인다.

### 10. 여러 인스턴스로 확장할 때 "이벤트 기반 즉시 처리"가 겪는 문제

지금은 서버가 1대라 쿠폰이 오픈되는 이벤트가 발생하면 그 즉시 Stream을 구독하는 방식이 잘 동작하는데, 서버가 여러 대로 늘어나면 "누가 그 이벤트를 처리할지"를 정하는 문제가 생길 것 같습니다.

현업에서는 이런 상황을 보통 어떻게 해결하는지 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

Redis를 이중화(2대)한다면 보통 하나는 master, 하나는 slave로 구성한다. slave는 읽기 전용으로만 쓰고, 실제 쓰기·처리는 master에서 담당한다.

애플리케이션 서버가 여러 대로 늘어나더라도, Redis가 발행하는 이벤트(Stream)는 컨슈머 그룹 메커니즘을 통해 여러 서버에 알아서 잘 분산될 것으로 예상된다.

다만 이론적인 예상에 그치지 말고, 실제로 서버를 여러 대 띄워서 직접 테스트해보는 걸 권한다.

이 과정에서 동시성 문제가 실제로 발생할 수 있으니, 처리 방식을 하나로 정하기보다 여러 패턴을 찾아보고 비교해보는 게 좋다.

**추가 코멘트**

Redis를 pub/sub 구조로 사용 중이라면, 서버를 확장한 이후 같은 이벤트가 여러 서버에 중복으로 발행되는 문제가 생길 수 있다.

pub/sub은 발행된 메시지를 그 시점에 구독 중인 모든 구독자에게 각각 전달하는 방식이라, 서버가 여러 대가 되면 각 서버가 동일한 이벤트를 중복으로 받게 되기 때문이다.

서버를 확장하기 전에, 지금 Redis Stream과 컨슈머 그룹(consumer group)을 사용하고 있는지 먼저 확인이 필요하다.

Stream + 컨슈머 그룹 구조라면 같은 그룹 내 컨슈머들이 메시지를 나눠 가져가므로 이런 중복 문제가 발생하지 않는다.

</details>

### 9. 사후 검증에서 "한 번 통과하면 영구 제외"하는 방식이 맞는지

<summary><strong>답변 보기</strong></summary>

한 번 확정된 대상을 영구 제외하는 방향은 필요해 보인다.

다만 이후에 그 데이터가 실제로 다시 바뀌는 경우(예: 취소·환불 등 사후 변경)를 대비해서, 데이터가 변경될 때 이벤트를 발생시켜 "언제 바뀌었는지" 시각을 기록해두고, 그 기록을 근거로 다시 조회하도록 설계하면 된다.

즉 무조건 다시 스캔하는 대신, 변경 이벤트가 발생한 것만 갱신된 시간을 기준으로 골라서 재검증하는 방식이다.

</details>

### 10. 여러 인스턴스로 확장할 때 "이벤트 기반 즉시 처리"가 겪는 문제

지금은 서버가 1대라 쿠폰이 오픈되는 이벤트가 발생하면 그 즉시 Stream을 구독하는 방식이 잘 동작하는데, 서버가 여러 대로 늘어나면 "누가 그 이벤트를 처리할지"를 정하는 문제가 생길 것 같습니다.

현업에서는 이런 상황을 보통 어떻게 해결하는지 궁금합니다.

<details>
<summary><strong>답변 보기</strong></summary>

Redis를 이중화(2대)한다면 보통 하나는 master, 하나는 slave로 구성한다. slave는 읽기 전용으로만 쓰고, 실제 쓰기·처리는 master에서 담당한다.

애플리케이션 서버가 여러 대로 늘어나더라도, Redis가 발행하는 이벤트(Stream)는 컨슈머 그룹 메커니즘을 통해 여러 서버에 알아서 잘 분산될 것으로 예상된다.

다만 이론적인 예상에 그치지 말고, 실제로 서버를 여러 대 띄워서 직접 테스트해보는 걸 권한다.

이 과정에서 동시성 문제가 실제로 발생할 수 있으니, 처리 방식을 하나로 정하기보다 여러 패턴을 찾아보고 비교해보는 게 좋다.

**추가 코멘트**

Redis를 pub/sub 구조로 사용 중이라면, 서버를 확장한 이후 같은 이벤트가 여러 서버에 중복으로 발행되는 문제가 생길 수 있다.

pub/sub은 발행된 메시지를 그 시점에 구독 중인 모든 구독자에게 각각 전달하는 방식이라, 서버가 여러 대가 되면 각 서버가 동일한 이벤트를 중복으로 받게 되기 때문이다.

서버를 확장하기 전에, 지금 Redis Stream과 컨슈머 그룹(consumer group)을 사용하고 있는지 먼저 확인이 필요하다.

Stream + 컨슈머 그룹 구조라면 같은 그룹 내 컨슈머들이 메시지를 나눠 가져가므로 이런 중복 문제가 발생하지 않는다.

</details>

</details>

<details>
<summary><strong>선착순 기준 관련</strong></summary>

"선착순을 어떤 기준(도착 순서, 처리 순서 등)으로 정의할지"에 따라 결과 해석이 완전히 달라지므로, 왜 그 기준(예: Redis 처리 순번을 기준으로 삼은 것)을 선택했는지를 명확히 설명할 수 있어야 한다.

</details>

<details>
<summary><strong>AI 활용</strong></summary>

AI 도구 사용은 권장한다. 실제 현업에서도 다양한 영역에서 활발히 쓰이고 있다.

다만 AI가 만든 산출물을 그대로 믿지 말고 반드시 검증하는 과정이 필요하며, "AI가 왜 그렇게 만들었는지 이해하고 쓰는 것"과 "이해 없이 그냥 가져다 쓰는 것"은 결과물의 완성도에서 분명한 차이를 만든다.

</details>

<details>
<summary><strong>면접/포트폴리오 준비</strong></summary>

면접이나 포트폴리오를 준비할 때는, 본인이 직접 담당하지 않은 영역이라도 프로젝트 전체 흐름을 설명할 수 있도록 미리 대비해두는 게 좋다.

특히 왜 이 기술 스택(Redis, Flyway, k6 등)을 선택했는지에 대한 근거를 각자 정리해두는 걸 권한다.

</details>

<details>
<summary><strong>발급 로그 UI</strong></summary>

발급 로그 표에서 “건”(화면 순서)과 “순번”(rank)은 굳이 두 컬럼으로 나누지 않고 하나로 합쳐도 무방하다.

</details>

<details>
<summary><strong>Kafka 도입 여부</strong></summary>

Kafka를 프로젝트에 도입해보는 경험 자체는 좋지만, "왜 굳이 Kafka여야 하는지"에 대한 명확한 이유 없이 사용 기술 목록에 넣는 것은 지양해야 한다.

</details>

<details>
<summary><strong>방법론 적용</strong></summary>

정해둔 개발 방법론이나 절차를 최대한 지키려고 노력하는 건 맞지만, 실제 프로젝트를 진행하다 보면 계획대로만 되지 않는 경우가 많다는 것도 감안해야 한다.

</details>

</details>
