## 1. 실행 방법

### 요구사항
- Docker / Docker Compose

### 클론
```bash
git clone https://github.com/UHO99/HighFive.git
cd HighFive
```

### 백엔드 + MySQL + Redis + K6 이미지
```bash
cd backend
docker compose build k6 && docker compose up -d --build
```
대시보드의 "테스트 시작" 버튼은 백엔드가 호스트 도커 소켓으로 k6 컨테이너를 띄워서 동작하는데, `k6` 서비스는
`docker compose up`만으로는 안 만들어진다.
그래서 `build k6`를 먼저 실행해 이미지를 준비한 다음 나머지를 띄운다.

확인:
```bash
curl http://localhost:8080/1
```

기본 계정은 `ureca`/`ureca`입니다. 바꾸고 싶으면 실행 시 환경변수로 넘기면 됩니다:
```bash
DB_USER=myuser DB_PASSWORD=mypass docker compose up -d
```

종료:
```bash
docker compose down       # 컨테이너만 정지 (데이터 유지)
docker compose down -v    # DB 데이터까지 초기화
```

### K6 시나리오 추가
시나리오 목록은 `backend/k6/` 디렉터리를 스캔하는 게 아니라, 백엔드의 `K6Scenario` enum
(`global/common/enums/K6Scenario.java`)에 정의된 것만 대시보드에 뜨고 실행도 된다 - 클라이언트가 보낸
시나리오 id로 임의의 파일을 실행시키지 못하게 막는 화이트리스트다. 그래서 새 시나리오를 추가하려면:

1. `backend/k6/내스크립트.js` 작성. `BASE_URL`/`COUPON_ID`를 기존 스크립트들과 같은 방식으로 읽어야 한다:
   ```js
   const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';
   const COUPON_ID = __ENV.COUPON_ID || '1';
   ```
2. `K6Scenario` enum에 상수 추가 (`id, file, name, description, rampUp, hold, targetVus, configurable, advanced`)
   - 앞의 일곱 개는 대시보드 시나리오 다이얼로그에 그대로 노출되는 값이고, 뒤의 두 개는 실행 전에
   어떤 입력창을 띄울지를 정한다:
   - `configurable` : 재고(`STOCK`)/동시접속(`MAX_VUS`) 입력. 재고는 선택한 쿠폰의 실제 값을 자동으로 쓴다.
   - `advanced` : 요청배수(`REQUEST_RATIO`)·유입방식(`ARRIVAL`/`DURATION`)·연타(`SPAM_RATIO`/`SPAM_CLICKS`)까지 입력.
     스크립트가 그 env var를 실제로 읽을 때만 true로 둘 것 - 안 읽는 스크립트에 true를 주면 입력창만
     뜨고 값은 무시된다.
3. 백엔드 재빌드 + k6 이미지 재빌드 (둘 다 해야 목록/실행이 새 시나리오를 반영한다):
   ```bash
   docker compose build k6 && docker compose up -d --build
   ```
   enum엔 추가했는데 이미지 빌드를 깜빡하면, 실행 시 "아직 이미지에 반영되지 않았습니다" 에러로 바로
   알려준다.

## 2. 멘토링 질문 리스트 (08.25 화요일)

### 1. 폴링 기반 화면 갱신의 성능 개선 방법
서버에 주기적으로 요청을 보내서 화면을 갱신하는 로직에서, 현업에서 성능 개선을 위해 사용하는 방법이 궁금합니다.

### 2. 리소스 생성 시점 vs 활성화 시점, 캐시 적재 타이밍
"쿠폰을 만드는 시점"과 "쿠폰을 실제로 오픈(판매 시작)하는 시점"이 분리되어 있고, 캐시(Redis)에 재고를 올리는 건 오픈하는 순간에만 합니다. 이렇게 "리소스를 생성하는 시점"과 "그 리소스를 실제로 활성화하는 시점"이 다를 때, 캐시에 값을 미리 올려둘지 활성화 시점에 올릴지를 실무에서는 어떤 기준으로 정하는지, 각각의 장단점이 궁금합니다.

### 3. 대량 이력 조회 API의 페이지네이션 방식
관리자가 특정 항목의 전체 이력(수만~수십만 건)을 조회하는 API가 있는데, 지금은 한 번에 다 내려주고 있습니다. 이력이 매우 커질 수 있는 조회 API에서, 실무 어드민 화면은 보통 cursor 방식과 offset 방식 중 뭘 쓰는지, "전체 조회"를 아예 허용 안 하는 정책은 어떤 기준으로 정하는지 궁금합니다.

### 4. 비관적 락 + 가상 스레드(Virtual Thread) 조합의 운영 안정성
동시성 제어에 DB 비관적 락과 Java의 가상 스레드(Virtual Thread)를 함께 써서 부하 테스트를 진행했습니다. 이 조합이 실제 운영 환경에서도 안정적인지, 혹시 가상 스레드와 락을 같이 쓸 때 특별히 주의해야 할 함정이 있는지 궁금합니다.

### 5. 캐시 복구 시, 상태값을 필터링해서 재계산하는 것이 맞는지
캐시(Redis)의 값이 유실됐을 때, DB에서 다시 계산해서 복구하는 로직이 있습니다. 이때 "현재 유효한 상태"의 건수만 세어서 복구하고 있는데(취소/만료된 건 제외), 이렇게 특정 상태만 필터링해서 복구값을 계산하는 게 맞는 접근인지, 실무에서는 캐시 복구 시 어떤 기준으로 재계산 범위를 정하는지 궁금합니다.

### 6. 부하 테스트 파라미터 — 자동 계산 vs 사람 입력의 기준
부하 테스트를 실행할 때, 어떤 값(예: 재고 수량)은 시스템이 자동으로 채워주고, 어떤 값(예: 요청 수)은 사람이 직접 입력하게 하고 있습니다. 부하 테스트 도구를 설계할 때, "자동으로 채워도 되는 값"과 "반드시 사람이 결정해야 하는 값"을 나누는 기준을 실무에서는 어떻게 잡는지 궁금합니다.

### 7. 짧은 이벤트를 대시보드에 실시간으로 보여주는 방법
전체 처리가 수십 초 안에 끝나는 짧은 이벤트를, 대시보드 화면에 실시간으로 보여주고 싶습니다. 이렇게 "지속 시간이 아주 짧은 이벤트"를 실시간 대시보드에 반영할 때, 폴링 주기를 얼마나 짧게 잡아야 하는지, 아니면 폴링이 아닌 다른 방식(WebSocket, SSE 등)을 언제부터 고려해야 하는지 실무 기준이 궁금합니다.

### 8. "처리된 순간"과 "기록된 시각"이 다를 때, 어느 걸 보여줘야 하는지
저희 시스템은 "실제로 처리가 확정된 순간"(원자적 연산이 일어난 시점)과, "그 결과가 DB에 저장되며 찍히는 시각"이 서로 다릅니다. 처리 자체는 즉시 확정되지만, DB 기록은 뒤늦게 배치로 반영되면서 그 순간의 시각이 아니라 "저장되는 시점"의 시각이 찍히기 때문입니다. 이렇게 "진짜 처리 순서"와 "기록에 남는 시각"이 어긋날 수 있는 시스템에서, 화면에는 어느 걸 기준으로 보여주는 게 맞는지, 실무에서는 이 둘의 불일치를 어떻게 다루는지 궁금합니다.

### 9. 사후 검증에서 "한 번 통과하면 영구 제외"하는 방식이 맞는지
데이터 정합성을 주기적으로 재검증하는 배치가 있는데, 한 번 "정상"으로 확인된 대상은 그 이후로 영원히 검증 대상에서 빠지도록 설계되어 있습니다. 이렇게 안 하면 검증 대상이 계속 누적되어 배치 부하가 무한정 커지기 때문인데, 이런 "한 번 통과하면 영구 제외"라는 방식이 안전한 설계인지, 아니면 안정성을 위해 주기적으로 재검사하는 게 더 맞는지, 실무에서는 이 트레이드오프를 어떻게 판단하는지 궁금합니다.

### 10. 여러 인스턴스로 확장할 때 "이벤트 기반 즉시 처리"가 겪는 문제
지금은 서버가 1대라 어떤 이벤트가 발생하면 그 즉시 반응하는 방식이 잘 동작하는데, 서버가 여러 대로 늘어나면 "누가 그 이벤트를 처리할지"를 정하는 문제가 생길 것 같습니다. 현업에서는 이런 상황을 보통 어떻게 해결하는지 궁금합니다.
